# Развёртывание на нескольких площадках

Запустите один Bootimus как **основной** (primary), где вы управляете всем, и по **реплике** на каждой удалённой площадке, которая зеркалирует основной и загружает локальных клиентов из локальных копий. Реплики доступны только для чтения: все изменения делаются на основном и попадают на реплики при их следующей синхронизации.

## Топология

```
                 HQ                                    Branch office
  +------------------------------+          +------------------------------+
  | Bootimus primary             |  HTTPS   | Bootimus replica             |
  | admin :8081  <---------------+----------+ pulls config and assets      |
  | boot  :8080                  |  every   | admin :8081 (read-only UI)   |
  | all changes are made here    |  5 min   | boot  :8080 serves clients   |
  +------------------------------+          +------------------------------+
                                                     | PXE / TFTP / HTTP
                                                     v
                                               branch clients
```

У каждой реплики своя база данных и свой каталог данных, поэтому филиал продолжает грузиться с последней удачной копии, даже когда WAN-канал лежит. Реплики никогда не пишут на основной.

## Настройка основного

На основном ничего не меняется, кроме создания токена для каждой реплики:

1. Откройте **Users** → **API Tokens** и создайте токен с именем площадки.
2. Выберите область действия:
   - `read` достаточно для клиентов, образов, групп, SAN-целей, темы, пользовательских профилей, инструментов и пользовательских файлов.
   - `admin` дополнительно синхронизирует **файлы автоустановки** и пароли BMC и CHAP. С токеном `read` эти пароли приходят скрытыми, и реплика сохраняет то, что у неё уже есть.
3. Скопируйте секрет `btk_...`; он показывается один раз.

Отдавайте админ-интерфейс основного по HTTPS (`--admin-tls`, см. [руководство по развёртыванию](deployment.md#защита-админ-интерфейса)), чтобы токен не передавался открытым текстом.

## Настройка реплики

Установите Bootimus на площадке как обычно, затем укажите ему основной:

```bash
bootimus serve \
  --replica-primary https://bootimus.hq.example.com:8081 \
  --replica-token btk_... \
  --replica-interval 5m
```

Или в `bootimus.yaml`:

```yaml
replica:
  primary_url: https://bootimus.hq.example.com:8081
  token: btk_...
  interval: 5m
  sync_isos: true
```

Переменные окружения: `BOOTIMUS_REPLICA_PRIMARY_URL`, `BOOTIMUS_REPLICA_TOKEN`, `BOOTIMUS_REPLICA_INTERVAL` и `BOOTIMUS_REPLICA_SYNC_ISOS`. Минимальный интервал — 30 секунд.

Реплика синхронизируется один раз при старте и затем через каждый интервал. Её админ-интерфейс показывает баннер с именем основного и временем последней успешной синхронизации, а любое создание, изменение или удаление отвечает `409 Conflict` с указанием на основной. Локальными пользователями и API-токенами на реплике по-прежнему можно управлять, чтобы вы могли в неё войти.

Включите `--proxy-dhcp` на реплике, если на площадке нет DHCP-сервера с поддержкой PXE, точно так же, как для автономной установки.

## Что синхронизируется, а что нет

| Синхронизируется с основного | Остаётся локальным у каждого экземпляра |
|------------------------------|-----------------------------------------|
| Клиенты (имя, группа, разрешённые образы, настройки BMC, файл автоустановки, SAN-цель) | Логи загрузок, счётчики загрузок и время последней загрузки |
| Группы клиентов | Аппаратная инвентаризация |
| Образы и группы образов (метаданные, метод загрузки, параметры загрузки, выбор WinPE) | Действия следующей загрузки и Wake-on-LAN |
| SAN-цели | Обнаруженные клиенты, которые грузились только на площадке |
| Тема меню загрузки | Обратные вызовы и статус установки |
| Пользовательские профили дистрибутивов | Пользователи, API-токены и журнал аудита |
| Включённые инструменты загрузки и их файлы | Запланированные задачи и вебхуки |
| Файлы автоустановки (только с токеном admin) | Кластеры Kubernetes и регистрация узлов |
| Пользовательские файлы | Настройки обслуживания |
| Имя активного набора загрузчиков (файлы набора уже должны быть на реплике) | Файлы пользовательских наборов загрузчиков |

Строки, исчезнувшие с основного, удаляются с реплики, с одним исключением: клиенты, обнаруженные на площадке и никогда не переведённые в статические на основном, не трогаются. Действия следующей загрузки намеренно не зеркалируются, потому что одноразовое действие, уже использованное на площадке, иначе применилось бы повторно при следующей синхронизации.

## Раздача ISO локально или с основного

При `sync_isos: true` (по умолчанию) реплика скачивает каждый включённый ISO с основного, извлекает ядра и initrd локально и обслуживает клиентов со своего диска. Первая синхронизация большой библиотеки занимает время; в это время реплика продолжает раздавать уже имеющиеся образы, а последующие синхронизации передают только файлы, размер которых изменился.

При `sync_isos: false` реплика хранит только метаданные и направляет пункты меню загрузки на порт загрузки основного, так что клиенты площадки тянут ISO и файлы загрузки через WAN. Образам с методами загрузки NBD или NFS нужны файлы локально, и в этом режиме они не загрузятся. Скрипты автоустановки всегда отдаёт сама реплика.

Если скачивание не удалось, этот образ до следующей успешной синхронизации использует URL основного.

## Пропускная способность

- Синхронизации метаданных — это небольшие JSON-списки, они выполняются каждый интервал.
- ISO скачиваются один раз и повторно только при изменении их размера на основном.
- Манифест с основного позволяет реплике пропускать виды данных, не менявшиеся с последнего запуска.
- Уменьшайте интервал только если нужно более быстрое распространение; на реплике есть и кнопка **Sync now**.

## Когда основной недоступен

Реплика продолжает отдавать своё последнее удачное состояние. Синхронизация помечается как неудачная, баннер показывает ошибку, а остальные виды данных в этом запуске пропускаются, а не применяются наполовину. При неудачном запуске локально ничего не удаляется. Синхронизация автоматически возобновляется, когда основной снова отвечает.

## Мониторинг

На вкладке **Server Info** реплики есть карточка **Replica**, где по каждому виду данных указано, успешна ли последняя синхронизация, сколько строк на основном и сколько изменено или удалено. Те же данные доступны через API, а `GET /api/me` содержит объект `replica`, чтобы скрипты понимали, с каким экземпляром они работают.

## API

```bash
# Replica: status of the last sync
curl -H "Authorization: Bearer $TOKEN" https://branch:8081/api/replica/status

# Replica: sync now
curl -X POST -H "Authorization: Bearer $TOKEN" https://branch:8081/api/replica/sync

# Primary: what a replica reads
curl -H "Authorization: Bearer $TOKEN" https://hq:8081/api/sync/manifest
```

Основной предоставляет репликам `GET /api/sync/manifest`, `GET /api/sync/tool-files?name=` и `GET /api/sync/asset?kind=iso|tool|file`; все три принимают токены с областью read.
